# 设计取舍与踩坑记录

这份文档记录 skill-bootstrap 的**每一个非显然决定**背后的理由，以及在实现过程中真实踩到的坑。
目的不是解释「代码做了什么」（看代码即可），而是回答「为什么不那样做」。

---

## 一、为什么是「首次调用惰性引导」

先穷举了所有可能的时机：

| 时机 | 可行性 | 原因 |
|---|---|---|
| 安装后自动装（post-install hook） | ❌ | Agent Skills 规范只约定文件结构与加载方式，不含依赖管理；WorkBuddy 无任何安装期钩子；Claude Code 有 39 个 hook 事件但**没有 `PostInstall`**，最接近的 `SessionStart` / `Setup` 属于宿主专有配置且每次会话都会跑 |
| skill 被加载时 | ❌ | 规范里「加载」只指把 `SKILL.md` 读进上下文，不执行代码 |
| **首次调用脚本时** | ✅ | 唯一**通用**时机。两个宿主行为一致，技能目录里不需要任何宿主专有配置 |
| 手工 `pip install` | ⚠️ | 仍然是兜底选项，但不该是**唯一**选项 |

选第三条。附带好处：一次安装后永久生效，之后每次调用只付出约 10ms 的探测开销。

---

## 二、探测用 `find_spec`，不用 `import`

```python
importlib.util.find_spec("rapidocr_onnxruntime")   # 只查规格，约 1ms
```

对比：

| 做法 | 代价 |
|---|---|
| `import rapidocr_onnxruntime` | 触发 onnxruntime 加载，**2~3 秒**。而这是每次调用都要付的 |
| 子进程 `python -c "import ..."` | 每个候选解释器都要起一次进程，几百毫秒 |

`find_spec` 只解析模块规格，不执行模块代码。这是快速路径能压到 10ms 量级的关键。

> 唯一代价：`find_spec` 对「已装但导入即崩」的模块会误判为可用。实务中极少见，且真出现时报错信息也比「假装没装」更有诊断价值。

---

## 三、复用优先于安装

缺依赖时的第一反应是「装」。但**先找找本机有没有已经装好的解释器**更划算：

```
缺失
 ├─ 1) 遍历候选解释器，找一个已装全部所需模块的 ──► 直接切过去（一次都不装）
 ├─ 2) 没有 ──► 建独立 venv 装
 └─ 3) 都不行 ──► 兜底装进当前解释器
```

实测：在「本机已有依赖齐全的解释器」的场景下，第 1 步命中，**总耗时等于一次解释器启动**，没有任何下载。
这在开发机上很常见 —— 作者本机早就有依赖，不该为了一次调用白等两分钟。

候选来源只有一处定义：若 `<skill>/scripts/env.py` 存在且暴露 `iter_candidates()`，引擎复用它；
否则用内置候选（运行时 venv → `deps.json` 指定的额外解释器 → PATH 上的 `python` / `python3` / `py`）。这样不会出现两套候选逻辑漂移。

---

## 四、装进独立 venv，而不是当前解释器

| 方案 | 问题 |
|---|---|
| 装进当前解释器 | 会改动调用者的环境。托管 venv、企业受管 Python、只读环境里直接失败，且污染难以回收 |
| 装进 skill 目录（`.runtime/`） | 每份副本各占一份体积；插件按版本目录缓存时，每次更新都要重装；共享盘只读时失败 |
| **装进 `~/<runtime_dir>/venv`** | 跨副本共享、只装一次、不动宿主环境。代价是不再「整目录拷走即用」—— 但「首次调用自动装」正好补上了这个代价 |

于是做成三级回退：环境变量 → 用户级 → skill 本地 → 当前解释器。
**排在前面不等于一定用** —— 只有可写的候选才进入列表。

---

## 五、失败不重试

初版在 pip 失败后会「换下一个安装位置再试」。这是个假动作：

失败原因是**缺包 / 无网 / 平台 wheel 不符**，与安装到哪个目录**毫无关系**。
换个位置重试只会把同一份错误打印三遍，让用户以为「试了三次都不行」，实际上是同一个问题。

改成：位置只在「venv 建不出来」时才换；pip 只执行一次，失败即止。

## 六、`--check` 不能有副作用

初版用 `mkdir` 试探目录可写性：

```python
try:
    parent.mkdir(parents=True, exist_ok=True)   # 留下空目录
    ...
```

结果 `--check`（一个只读操作）会在用户家目录和 skill 目录下各留一个空的 `.my-skill/` 与 `.runtime/`。

改成向上找**最近的已存在祖先**再判断可写性：

```python
def _writable(path):
    p = Path(path)
    while not p.exists():
        parent = p.parent
        if parent == p:
            return False
        p = parent
    return os.access(str(p), os.W_OK)
```

代价是判断略保守（父目录可写 ≠ 一定能创建），但**副作用为零**更重要。

## 七、四个真实踩的坑

### 坑 1：挂载点放 `main()` 里根本不执行 ⚠️ 最重要

首测直接报「缺少 Pillow」。根因：

```python
# convert.py
try:
    from PIL import Image
except ImportError:
    sys.exit(2)              # ← 模块级，导入失败就退出

# pipeline.py
import convert               # ← 模块级 import，上面那行先执行了
```

`pipeline.py` 在**模块级**就 `import convert`，而 `convert.py` 的 `Pillow` 导入在模块级 `try` 块里、失败即 `sys.exit`。
挂载点写在 `main()` 里**永远等不到执行**。

**结论**：挂载点必须插在模块顶部，早于所有第三方导入。
`init_skill_runtime.py` 用 `ast` 定位插入点：文档字符串之后、`__future__` 导入之后、其余一切之前；插入后再 `ast.parse` 校验，语法有问题自动回滚原文件。

### 坑 2：探测留下空目录

见上文第六节。`--check` 是只读的，不该产生任何文件系统变化。

### 坑 3：测试因为工作目录而**假通过**

写「故意破坏离线包（删掉某个 wheel），验证是否立即报错」的测试时，结果 `EXIT=0`。
排查发现 `local_wheel_dirs()` 会扫**当前工作目录**，而测试的 cwd 里恰好有一份完整的 `wheelhouse/`，pip 从那里找到了缺失的包。

这个「假通过」反而是好消息 —— 它证明了多目录回退是有效的。但测试设计得改：**换到干净 cwd** 才能复现预期失败。
后来把自检的 wheel 目录放在一个**不在自动发现名单里**的路径（`wheels_ok` 而非 `wheelhouse`），并显式用环境变量指定，彻底消除这类干扰。

> 教训：测「失败路径」时，必须确认失败**真的会发生**，而不是被兜底逻辑救回来了。

### 坑 4：并行编辑同一文件会**静默丢改动**

一条消息里对同一个文件发 6 个编辑，只有**最后一个**生效，其余静默丢失 —— 因为每个编辑都基于同一份旧内容做替换，后写覆盖前写。

改法：要么逐个串行编辑，要么写一个**带断言的批量替换脚本**（每处替换都校验「原文出现次数 == 1」，不满足即报错停止）。

### 附带：输出顺序会被管道打乱

引导器的消息跑到子进程输出**后面**。原因是 stdout 被重定向时是块缓冲，而子进程直接写 fd。
修法：`print(..., flush=True)`。

## 八、已知局限

| 局限 | 说明 |
|---|---|
| 只适用于 Python 技能 | 引擎本身是 Python。Node / Go 技能需要各自的语言版本 |
| `find_spec` 的误判 | 见第二节。极少数「已装但导入崩」的包会被判为可用 |
| 首次安装耗时 | 建 venv + 装包约 1~2 分钟（视依赖量）。无法避免，只能通过「复用已就绪解释器」在不必要时跳过 |
| 不管理系统级依赖 | 需要 `apt install` 的系统库（如字体、`libGL`）不在职责内，需技能自己分平台处理 |
| 引擎需人工同步 | 引擎文件在各 skill 间应保持一致。升级时需重新复制到每个 skill（`init_skill_runtime.py` 幂等，可直接重跑） |

## 九、自检为什么能离线

自检要验证「纯离线安装」，但被测依赖从哪来？不能联网下载。

解法：**用标准库现造一个合法 wheel**。wheel 本质是个 zip，含：

```
dummy_dep.py
dummy_dep-0.0.1.dist-info/METADATA
dummy_dep-0.0.1.dist-info/WHEEL
dummy_dep-0.0.1.dist-info/RECORD
```

约 30 行代码即可生成，pip 完全接受。于是自检可以：

1. 造 wheel → 放进临时目录
2. 造一个迷你 skill（含**模块级重依赖导入**的入口脚本）
3. 用脚手架给它装引导器
4. 从零依赖的解释器启动入口脚本 → 引擎应建 venv、`--no-index` 装包、重跑成功

全程无网，且验证的是**真实的 pip 安装链路**，不是打桩。

## 十、与本仓库 image-toolkit 的关系

本技能是 `image-toolkit` 中 `scripts/bootstrap.py` 那套做法的**通用化抽取**，不是同一份文件的复制：

| | image-toolkit 的 `bootstrap.py` | 本技能的 `skill_bootstrap.py` |
|---|---|---|
| 定位 | 该技能专用 | 通用引擎，可原样复制到任意 skill |
| 依赖清单 | 硬编码在源码里 | 外置到 `deps.json` |
| 环境变量前缀 | 固定 `IMAGE_TOOLKIT_` | 由 `deps.json` 的 `env_prefix` 决定 |
| 候选解释器 | 依赖同目录 `env.py` | 有内置候选；若同目录存在 `env.py` 则优先复用它 |
| 命令行 | 固定分组（`--no-ocr`） | 任意分组（`--groups` / `--list-groups`） |

抽取时刻意保留了 image-toolkit 已经验证过的行为（快速路径 ~10ms、复用优先、失败不重试、`--check` 无副作用），
只把「哪些包、叫什么名字、前缀是什么」这几件真正因技能而异的事挪进了配置。

> 迁移已有技能时不必强行替换其现有引导器 —— 两者行为一致，都基于同一套已验证的机制。
> 新技能建议直接用本技能接入。
