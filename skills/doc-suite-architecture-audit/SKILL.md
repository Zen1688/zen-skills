# 成套文档的架构级审阅

## 为什么不能只靠"通读印象"

人对长文档的判断会被**篇幅**和**文风**带偏：写得密的地方看起来"完整"，写得疏的地方看着"不完整"，但真正的问题往往在**引用断链、术语漏收、版本过期、数字算错**这类可机械核验的地方。本技能的价值就是把"我觉得挺全"换成"这 4 项可复核的计数"。

## 五维判据（逐个对应到可执行检查）

| 维度 | 检查手段 | 失败信号 |
| --- | --- | --- |
| **完整性** | 术语覆盖矩阵（正文出现的名词 vs 词典/附录是否收录）、章节对称性（同类分册是否都有求职章/实战章） | 正文有词词典无；A 册有 X 章 B 册缺 |
| **连贯性** | 交叉引用解析（每条"见 X.X 节/第 N 章"是否真有目标）、依赖基线表 vs 代码实际用到的依赖、**贯穿元素一致性**（同一实体/案例跨分册的写法与属性比对，见 §8） | 引用了不存在的章节；基线表漏登依赖；同一错误码在两册有两套处置 |
| **可读性** | 结构密度量化（行/章、表格行占比、代码块数）、图数量（C4/时序/ASCII）、全局目录存在性 | 各册密度差 2 倍以上；0 张图；无 TOC |
| **能力闭环性** | 逐册验收清单条目分类（认知型"能讲/能算" vs 交付型"能跑出/能交付"）、是否有跨册总验收 | 高级册验收全是认知型，无可交付物 |
| **可实践性** | 版本时效核验（文档声明基线 vs 各版本号的实际发布情况）、关键数字复算 | 声明 2026 基线却写 2024 的版本号；示例算错 |

## 执行流程

### 1. 先量化结构，再读内容

不要一上来通读。先跑 `scripts/audit_checks.py metrics` 拿到基线表（行数/章数/节数/表格行/代码块/行/章）。密度失衡和"无图无目录"在这一步就能看出来。

### 2. 通读全文（必须，不可用抽样代替）

量化只定位"哪里可疑"，判"缺什么"必须知道全文写了什么。分册多时按册读完，不要只读目录。

### 3. 交叉引用穷尽解析

```bash
python scripts/audit_checks.py refs <目录>
```

把形如 `见 7.2 节` `见提高篇 5.5 节` `详见第 10 章` `见第 4 章` 的引用全抓出来，**逐条回原文确认目标存在**。这一步专抓"承诺了但没写"的失效引用——最容易在迭代中产生，因为改章节顺序时不会有人回头改引用。

> ⚠️ **脚本只抓"带编号"的引用，抓不到"文字承诺"**。实测踩过：某册写着「Java 侧加载推理，**提高篇 DJL / ONNX 章节展开**」——三个字承诺，一个编号都没有，`refs` 扫不出来，但它是全篇最严重的失效引用（目标册根本不存在该章节）。
> **所以引用核验必须双轨**：`refs` 跑编号引用 + 通读时对「详见 / 展开 / 详述 / 见某篇某章」这类**无编号承诺词**逐个回查。判据：承诺词 + 目标册名 ⇒ 去目标册搜该主题的**章节标题**（不是搜关键词出现次数——出现 1 次可能只是选型表里的一行备注）。

### 4. 术语覆盖矩阵

```bash
python scripts/audit_checks.py terms <目录> <词典文件> --words 词1,词2,...
```

列出"正文出现 N 次但词典未收录"的词。注意两点：
- **计数为 1 的词往往是漏网的专有名词**（SmoothQuant、MinHash 这类）；
- 也要反向看"词典有但正文 0 次"——不一定是错（词典可作超集），但要确认定位是否讲清楚。

### 5. 关键数字复算

凡是文档里给了公式又给了结果的（显存估算、参数量、FLOPs、百分比、并发数），**用 Python 重算一遍**。经验：作者算错通常只错在**输入参数**（如把 48 层的模型写成 40 层），公式本身是对的——所以先核对参数来源（去 HF `config.json` / 官方文档查），再决定要不要改公式。

### 6. 版本时效核验

把文档声明的"撰写基线年月"和文中所有版本号对照。**这类问题最隐蔽**：文档 2026 年写，却引用 2024 年的话术，读者照着命令装不上。

```bash
python scripts/audit_checks.py versions <目录>   # 抓出所有版本号写法
```

再核实 2~3 个关键项的最新版本（WebSearch 查官方 release notes / PyPI / Docker Hub 的发布日期最可靠）。

> **实测提醒**：`versions` 的输出**噪声很大**——它会把代码里的数值字面量（`temperature=0.2`、`top_k` 的 `0.1`）一并抓出来。别逐行看，**只看出现次数最多的十几项里有没有 X.Y 或 X.Y.Z 形态的包版本**（如 `0.30.0`、`2.x`、`1.0.0`），那些才是真版本号。宁可多花 30 秒过滤，也不要被噪声劝退而跳过时效核查——时效问题恰恰是本技能最独特、最容易漏的一类发现。

### 7. 事实复算与时效核验的取证纪律

- 参数来源必须**可引用**：模型层数/头数去 HF 仓库的 `config.json`，版本去官方 release notes。写进结论时带上来源，否则读者无法复核。
- 只错参数、不错公式的情况最常见。**先核参数，再考虑改公式**；如果结论由别的因素驱动（例如"需要几张卡"由吞吐而非显存决定），要明确指出**结论不受影响**，避免把小事说成大事故。

### 8. 贯穿元素一致性（实体 / 案例 / 术语的跨册比对）

成套文档若无统一主编，**同一个虚构实体在不同分册会各自演化**——这类矛盾「通读一遍根本发现不了」，因为你读 02 时不会记得 03 那页写的是另一个写法。

✅ **手段：先建实体清单，再逐实体 grep 全库**

```bash
# 1) 找出跨册复现的实体（位号 / 型号 / 错误码 / 人名 / 公司名 / 案例变量名）
grep -rn 'Err-77\|0x5F\|E102\|E-102\|IRB-6700' --include=*.md .
```

实测产出（某 3 分册手册，同一「设备运维」案例域）：

| 矛盾类型 | 实况 | 为什么致命 |
| --- | --- | --- |
| **写法分裂** | 分册 A `E-102` vs 分册 B `E102`；`Err-77`（十进） vs `0x5F`（十六进制） | 读者以为是两个设备 / 两套规范 |
| **属性矛盾** ⚠️ | 同一个 `Err-77`：A 册手册写「换**电源模块**」，B 册标注答案写「换**主板电容**」 | **最伤专业感**——同一故障两套处置，比命名不一致严重得多 |
| **域内混入异域** | 主线是设备运维，却有一道题是「客服 Agent（查单/退款）」 | 叙事断裂，读者不知道是不是同一家公司 |

**五条纪律**：

1. **实体清单要覆盖"属性"而非只覆盖"名字"**：先抓写法，再对每个实体的**关键属性**（处置措施、数值、单位、时间）逐处比对——属性矛盾才是硬伤。
2. **占比决定代价**：先数「该域已存在的资产处数」。若 A 册已有 6 处、B 册已有 2 处，那么缺口是**口径统一**而不是「从零新建」——**上游对代价的评估很可能因此高估一档**（实测：L → S+M）。
3. **顺手查合规**：教材/规范里的示例若用了**真实在售商标**（如某机械臂型号），有暗示背书与过期双重风险，建议替换为虚构代号。
4. **区分"待修"与"可留"**：异域混入（如客服支线）不一定要改，可以在「案例设定页」里声明它是同公司的**另一条业务线**——比强行改写更省事、更真实。
5. **验收时限定范围** ⚠️：落地后复验「旧写法应为 0 命中」时，**必须把规划稿 / 方案文档排除在扫描范围外**——它们按证据链保留了改动前的快照（「改前是 `E102` / `0x5F`」本身就是证据）。用 `grep -rn ... .` 会把**证据**误判成**缺陷**，白改一轮。正确口径：**显式列举被审正文**（`grep -n 'E102\|0x5F' README.md 01-*.md 02-*.md ...`），验收语写作「**被审正文内** 0 命中」。修复完成后，规划稿文首补一句「下文行号与实体写法均为改动前快照，不随正文更新」，把这条边界固化下来。

### 9. 大缺口要拆成"分层方案"，并声明哪层不做

一个 L 级缺口直接给「全做/不做」是逼用户二选一。更好的做法是拆成**代价递增的若干层**，让用户只拍板做到第几层：

| 层 | 内容 | 代价 |
| --- | --- | --- |
| **L0 入口层** | 新增一个「设定页 / 术语表」作为唯一事实源（落位：不新增章，零重编号） | S |
| **L1 口径层** | 统一命名与口径（纯替换，0 新增行，可 `grep` 验收） | S |
| **L2 外壳层** | 给缺失分册补业务外壳（**只改叙事与常量，不动可运行代码**） | M |
| **L3 深挖层** | 逐章替换为业务示例 | L |

⚠️ **并且必须写明 L3 为什么不做**——实测理由：会涉及全库 91 个代码块，且把**原理层**（数学 / 框架 / 部署 / 量化）的示例绑死在单一业务上，会**削弱文档作为可迁移方法论的价值**。**"不做"的边界声明和"要做"的清单同等重要**，否则下一轮评审又会把它当缺口重提。

## 输出规范

- **结论先行**：先给五维判定表，再展开。
- **每条缺口必须带 `文件:行号` 证据**，不接受"某处"。
- **按 P0/P1/P2 分级**：P0=事实错误或自相矛盾（会让读者做错事）；P1=结构缺口（影响学习效果）；P2=可选优化。
- **必须单列一段"已核验无误"**：证明审阅是全覆盖而非只看问题，也让用户知道哪些不用动。
- **末尾给编号待拍板清单**，供用户逐项拍板（1）2）3）格式）。
- 若用户说"不落地文档"，就**只输出清单，不动文件**。

### 把清单落地成独立方案文档时的规范

用户常接着说"把审查结果落地到文档，文章名 X.md"——注意是**新建方案文档**，不是改正文。此时按以下结构组织（实测好用）：

| 章节 | 要点 |
| --- | --- |
| 文件头表 | 文档性质、审阅对象、**对象规模**（文件/行/章数）、审阅方法、审阅基线、生成时间、**落实状态**、复核工具路径 |
| 〇 阅读指南 | 定义 P0/P1/P2 与**改动代价档**，交代「状态」列与拍板后如何流转 |
| 一 总体判定 | 五维×分册矩阵 + 一句话结论 + 结构指标表 |
| 二 问题清单总览 | 一页速览表：`编号 / 级别 / 维度 / 位置 / 一句话 / 代价 / 状态` |
| 三~五 | P0 / P1 / P2 逐条展开。P0 用**统一字段表**（位置 / 级别 / 代价 / 现象证据 / 影响 / 建议方案 / 处置建议），P1 起可压缩为列表格 |
| 六 已核验无误 | 单列，证明覆盖度 |
| 七 实施建议 | **分批次推进表**，排序原则：先止损（无维护负债）→ 再补链 → 最后引入需持续维护的资产 |
| 八 待拍板清单 | 编号表，含「议题 / 选项 / 建议」三列 |
| 附录 | A 复核方法（可复现命令）；B **变更记录空表**（待实施时填）；C 术语覆盖矩阵 |

**改动代价分三档**（用户拍板最关心「改起来的代价」，必须标注并按此排序）：

| 档 | 含义 | 风险 |
| --- | --- | --- |
| **S 声明级** | 改 1~2 行，不动结构 | 零风险 |
| **M 增量级** | 新增段落/条目/表行，不动既有编号 | 低 |
| **L 结构级** | 新增章节，或引入**需持续维护的资产**（架构图、可运行代码） | 高，产生时效负债 |

**落位设计要顺手算重编号代价**：能给「零重编号」方案就别给重编号方案。实测两例——新小节插在**末尾空闲编号**（第 8 章已有 8.1/8.2/8.3 ⇒ 用 8.4）；新章插在**末章与 `## 结语` 之间**（结语非章级，插章不触发重编号）。

## 坑

- **别把"篇幅短"当"内容少"**：要发行/章、表格行占比一起看。03 册 55 行/章 vs 02 册 117 行/章，才是可信的"薄"。
- **`\&` `\*` 这类转义不是错误**：Markdown 表格里 `Weights \& Biases` 是正确写法，别报成 bug。
- **同一缩写的合法重复不是重复**：如 `CV`=Computer Vision / Cross-Validation。要用"同形缩写"的口径去看，而不是当重复词条删掉。
- **改了文档的引用编号就等于改了整套引用**：审阅时发现要"重编号"的建议，必须同时列出所有受影响的交叉引用位置。
- **结构计数必须写清口径**：`text.count("```")`（全文计数，会被**正文里的内联三反引号**污染）与 `lines.count("```")`（列表里恰好等于 ``` 的行数，与奇偶无关）是两个完全不同的量。审阅脚本输出这类计数时**必须带单位**——否则一个看似合理的 "5" 就能骗过整轮校验。写正文描述用**单反引号**（`` `mermaid` ``），把三反引号留给真正的围栏。
- **"0 次"和"1 次"要复核**：初审写"某关键词全篇 0 次"，复核时用 `grep -c` 重跑，实为 1 次——**结论方向可能不变，但证据精度必须修正**。凡是写进结论的计数，落笔前重跑一次；近似值不要当精确值写。
- **代价档不能凭"印象厚度"定，必须取证后重估**：实测一例——上游把「三册无贯穿业务案例」定为 **L**（"代价大、收益长期"），取证后数出该案例域**已经有 8 处资产**，真实缺口只是「口径统一 + 一个入口」，**代价降为 S+M**。代价的本质是「**要改多少处**」，不是「听起来多复杂」；审阅时若发现原代价评估偏高，**要明确写出修正**（`L → S+M`）并给处数依据，否则用户会因误判的代价错过低成本高收益的改动。
- **反过来也要防低估**：若缺口是"新增需持续维护的资产"（架构图 / 可运行代码 / 时效敏感的命令），代价**不得降档**——这类负债会随版本迭代持续产生维护成本。
