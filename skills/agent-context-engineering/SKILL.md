# 上下文工程 GSSC 流水线（agent-context-engineering）

## R — 原理锚点

> 上下文 = 采样时包含的 tokens；"在上下文中思考"。（第9章 9.1 节）

这段为什么重要：上下文不是"背景设定"而是每一次 LLM 调用的实际输入预算。所有优化（筛选、压缩、分层）都围绕"在有限 token 内放最该放的内容"展开，这是本 skill 的统一定义起点。

> 有效上下文解剖学：系统提示 / 工具 / MVTS / 精选示例。（第9章 9.2.1 节）

这段为什么重要：它给出上下文四构件清单，避免只盯"系统提示"。工具与精选示例同样是上下文的一部分，漏掉任一构件都会让 Agent 行为失准。

> GSSC 流水线：Gather（多源+容错）→ Select（相关性×relevance_weight 0.7 + 近因×recency_weight 0.3 加权、贪心）→ Structure（五分区模板）→ Compress（分区压缩保结构）。（第9章 9.3 节）

这段为什么重要：GSSC 是本书自创的可复用、可度量、可演进的上下文组装方法，把"凭感觉拼 prompt"变成四步流水线，是后续所有实现的核心骨架。

> 上下文是有限资源、边际收益递减。（第9章 9.2 节）

这段为什么重要：它解释为什么不能"无限扩窗"。窗口越长回忆越差（context rot），必须谨慎筛选入窗 tokens 而非堆量。

> 上下文窗口以 Token 计，须精确管理避免超限。（第3章 3.2.2.3 节）

这段为什么重要：token 是计费与长记忆的基础单位，超限会直接报错，精确管理是工程落地的硬约束。

> 分层上下文三层架构：即时访问（TerminalTool）+ 会话记忆（MemoryTool）+ 持久笔记（NoteTool）。（第9章 9.6 节）

这段为什么重要：单层上下文无法兼顾"即时探索、会话连续性、跨会话持久"，分层让不同生命周期的信息各归其位，是长程任务断点续传的基础。

## I — 骨架

### I.0 心智模型与解剖（第9章 9.1 / 9.2.1 节）
- 心智模型：上下文 = 采样时包含的 tokens；每次调用前以可复用、可度量、可演进方式拼装优化。
- 四构件（F2）：系统提示 / 工具 / MVTS（最小可行工具集）/ 精选示例。

### I.1 GSSC 流水线（第9章 9.3 节，本书自创，核心）

**G — Gather（多源采集 + 容错）**
- 从多源（记忆、检索、工具输出、笔记）采集候选上下文。
- 容错：单源失败不阻断整条流水线。

**S — Select（加权贪心筛选）**
- 打分：`score = relevance × relevance_weight(0.7) + recency × recency_weight(0.3)`。
- 策略：贪心选入，直到触达上下文预算（max_tokens）。
- 经验：先召回后精度（P5，轻触式先清深历史工具输出）。

**St — Structure（分区模板）**
```
[Role & Policies]
[Task]
[Evidence]
[Context]
[Output]
```
按分区把筛选后的内容落位，Evidence 放检索/工具证据，Context 放背景。

**C — Compress（分区压缩保结构）**
- 逐区压缩，保留分区结构与关键信号，不破坏 [Role & Policies]/[Task]/[Output] 等骨架。
- 先召回后精度：先清深历史工具输出等冗余，再精确保留高价值内容。

### I.2 分层上下文三层架构（第9章 9.6 节）
| 层 | 工具 | 生命周期 | 用途 |
|---|---|---|---|
| 即时访问 | TerminalTool | 单次交互 | 运行时即时探索代码库/文件系统 |
| 会话记忆 | MemoryTool | 当前会话 | 承载本轮对话连续性 |
| 持久笔记 | NoteTool | 跨会话 | 跨会话追踪、断点续传 |

### I.3 JIT 上下文 / 渐进式披露（第9章 9.2.2 节）
- 前置少量高价值上下文；运行时用 glob/grep 按需探索加载。
- 每步交互产生的新上下文指导下一步。
- 路径/时间戳等元数据辅助"是否加载"的决策。

### I.4 ContextBuilder 动态预算与 A/B（第9章 9.3.5 节，P6）
- 按任务复杂度动态调 `max_tokens`。
- 对 relevance_weight / recency_weight 做 A/B 实验。
- 生产环境用向量相似度替代关键词重叠做相关性判断。

### I.5 系统提示"最小必要信息集"（第9章 9.2.1 节，P2）
- 避两极：过度硬编码（脆弱 if-else）/ 过于空泛（缺具体信号）。
- 方法：先小提示试跑，再据表现补充，而非一次性堆满。

### I.6 通用原则清单（P 轨，可直接照做）
- P1 上下文有限、边际收益递减 → 谨慎筛选入窗 tokens。
- P3 工具职责单一、用 MVTS → 拒"臃肿工具集"，否则"选哪个工具"含混。
- P4 JIT + 混合策略 → 前置高价值上下文，运行时 glob/grep 按需探索。
- P7 窗口以 Token 计、精确管理避免超限。
- P8 缓解幻觉须引入 RAG/外部工具/多步自我验证。

## A1 — 案例

**C1. 无状态 Agent 忘记"我叫张三"（第8章 8.1.2 节）**
- 场景：重启后 Agent 丢失用户刚说的名字。
- 做法：证明需要记忆系统承载会话连续性。
- 可迁移教训：无状态实现无法跨重启保留信息，必须引入会话记忆层（MemoryTool）或持久笔记。

**C2. 智能文档问答助手（第8章 8.4 节）**
- 场景：基于文档的问答。
- 做法：RAG + Memory 闭环（加载 → 情景记忆 → 高级检索问答 → 报告）。
- 可迁移教训：检索与记忆协同 + 智能路由，是上下文工程中"外部知识进窗"的标准形态。

**C3. 长程代码库维护助手（第9章 9.6 节）**
- 场景：跨多轮维护大型代码库。
- 做法：TerminalTool 即时探索 + NoteTool 跨会话追踪 + ContextBuilder 筛选。
- 可迁移教训：分层上下文 + 断点续传，让长程任务在有限窗口内不丢关键状态。

**C4. 健康管理助手设计题（第8章 8.5 习题）**
- 场景：需记忆饮食/运动/睡眠多类信息。
- 做法：四类记忆分派到饮食/运动/睡眠等维度。
- 可迁移教训：按类型分派记忆，是"记忆过度设计"与"信息混淆"之间的折中套路。

## A2 — 触发场景

以下情况应调用本 skill（可判断，非空话）：
- 用户报告 Agent 聊几轮就忘了之前说过的内容（遗忘/无状态问题）→ 指向记忆层与分层架构。
- 用户要做"上下文压缩/筛选/组装"，或明确提到 GSSC、上下文工程。
- 用户遇到上下文腐蚀/污染：窗口越长表现越差、无效信息干扰。
- 用户上下文窗口超限报错（token 超限）→ 指向精确管理与 Compress。
- 用户系统提示写得过长或过短导致 Agent 行为混乱（过度硬编码 vs 过于空泛）。
- 用户工具集庞大导致"选哪个工具"含混（臃肿工具集）→ 指向 MVTS 与 JIT。
- 用户做长程任务（代码库维护、跨会话追踪）需要断点续传与分层上下文。
- 用户问"RAG 反而帮倒忙 / 检索召回低"→ 指向 ContextBuilder 与检索质量。

## E — 执行步骤

1. **盘点上下文四构件**：列出当前系统提示 / 工具 / MVTS / 精选示例各有什么。→ 产出物：构件清单；判断点：是否四者齐备、有无冗余。
2. **Gather 多源采集**：从记忆、检索、工具输出、笔记拉候选，单源失败不阻断。→ 产出物：候选上下文池；判断点：覆盖任务所需信息源。
3. **Select 加权贪心**：按 `relevance×0.7 + recency×0.3` 打分，贪心选入直到 `max_tokens` 预算。→ 产出物：入选内容；判断点：高价值近期内容优先、深历史冗余先清（先召回后精度）。
4. **Structure 分区落位**：填入模板 `[Role & Policies]/[Task]/[Evidence]/[Context]/[Output]`。→ 产出物：分区化 prompt 骨架；判断点：Evidence 与 Context 不串区。
5. **Compress 保结构压缩**：逐区压缩，保留骨架与关键信号。→ 产出物：压缩后上下文；判断点：是否仍超限、结构是否完整。
6. **按需分层与 JIT**：会话级用 MemoryTool，跨会话用 NoteTool，即时探索用 TerminalTool；运行时 glob/grep 按需加载。→ 产出物：分层方案；判断点：是否避免把全部信息一次性入窗。
7. **动态预算与验证**：按复杂度调 `max_tokens`，对权重做 A/B，生产用向量相似度；验证无超限、无关键信息漏选。→ 产出物：可度量配置；判断点：表现是否下降（见 B 段 A9）。

## B — 边界与失效条件

**上下文腐蚀与过量（第9章 9.2 节，A1）**
- context rot：tokens 增多时回忆能力反降；无限扩窗不能根治污染。→ 不能靠"堆窗口"解决，必须筛选/压缩。

**系统提示两极（第9章 9.2.1 节，A2）**
- 过度硬编码（易碎 if-else）vs 过于空泛（错假共享上下文）。→ 用"最小必要信息集"折中。

**工具与 JIT 风险（第9章 9.2.1 / 9.2.2 节，A3/A4）**
- 臃肿工具集：边界模糊使工具选择含混。
- JIT 探索：更慢；缺引导→误用工具/追死胡同/漏关键信息→上下文浪费。

**RAG 帮倒忙（第8章 8.3.1 / 8.3.5 节，A5）**
- 朴素 RAG 直拼引入噪声；查询与文档用词差异大时基础检索召回低；嵌入模型选错拖垮质量。

**记忆过度设计（第8章 8.1.3 / 第9章 9.2.1 节，A6）**
- 四层架构 + 过度硬编码系统提示维护成本高，应坚持最小必要。

**敏感与抽取失效（第8章 8.5 习题，A7/A8）**
- 误删敏感信息不彻底：向量/图库仅删记录不够。
- 语义记忆实体抽取可错：自动图谱可能错实体/关系。

**GSSC 自身失效（第9章 9.3 习题，A9）**
- Select 选错信息或 Compress 过度压缩 → 信息丢失、表现下降。→ 必须验证"无关键信息漏选"，权重/压缩率需 A/B 调优。

## 配套技能

本技能是 **AI Agent 全生命周期套件**（`zen-agent-suite`）的第 5/10 环。
从需求分析到交付运维，覆盖构建一个 AI Agent 产品的完整链路。

> **只装本技能不足以覆盖完整需求。** 若你正在做的是「创建 AI Agent/搭建智能体」这类完整任务，建议一并安装同套件的其他 9 个技能 —— 它们分别负责需求、设计、验证、运维等环节，缺环会导致流程断在中途。
