# Agent 需求分析与任务拆解

> 本 skill 为「行业通用实践」，非《Hello-Agents》教材蒸馏产物。用于补齐 Agent 产品生命周期的**需求分析**环节。

## R — 原理锚点

> 智能体适合处理「模糊、开放式、需要多步决策与工具交互」的任务；确定性、规则可穷举的流程应优先用传统软件或简单 LLM 调用。

这段为什么重要：它划定了 Agent 的「能力甜区」。需求分析的第一个决策不是「怎么拆」，而是「该不该用 Agent」——用错了技术栈，后面所有设计都是浪费。

> 需求分析的核心产物不是功能列表，而是**可验证的验收标准**（Definition of Done）。没有 DoD 的 Agent 项目会陷入「永远差一点」的范围蔓延。

这段为什么重要：Agent 输出天然不确定（同一问题多个正确答案），比传统软件更难「验收」。只有把验收标准在需求阶段就量化，交付阶段才有据可依。

> Agent 项目的失败，一半源于「把不该自动化的环节自动化了」，另一半源于「边界没划清，越做越多」。

这段为什么重要：它点出 Agent 需求分析的两个独特风险——过度自动化与范围蔓延，二者都应在需求阶段被拦截。

## I — 骨架

需求分析产出四件套，按顺序执行：

### 1. 适用性判定（四象限决策）

| 维度 | 问自己 | 偏向 |
|---|---|---|
| 任务模糊度 | 输入/输出是否开放、无唯一正确答案？ | 开放 → Agent |
| 决策步数 | 是否需要多步推理、中间依赖？ | 多步 → Agent |
| 环境交互 | 是否需要调用工具、检索、感知外部世界？ | 需要 → Agent |
| 规则完备性 | 流程能否被规则穷举？ | 能穷举 → 传统软件/规则引擎 |
| 错误成本 | 一步错是否不可接受（资金/安全/合规）？ | 不可接受 → 加人工兜底或不做 |
| 延迟要求 | 是否要求亚秒级确定性响应？ | 是 → 简单 LLM 调用，非长程 Agent |

**判定结论三选一**：用 Agent ／ 用简单 LLM 调用 ／ 不用 LLM（规则/传统软件）。每条结论必须附一句理由。

### 2. 任务拆解（三层模型）

```
业务目标 (Goal)
   └─ 任务 Task₁ … Taskₙ          ← 每个任务 = 一次可独立验收的智能体职责
        └─ 能力单元 (角色 / 工具 / 记忆 / 范式)   ← 支撑任务的四类资源
```

拆解产物 = **任务清单表**，每行：

| 任务 | 输入 | 输出 | 成功标准 | 依赖 |
|---|---|---|---|---|
| 意图识别 | 用户消息 | 意图标签+参数 | 准确率≥阈值 | — |

**拆解粒度判据**：
- 过粗：单个任务内隐含多个独立决策点（Agent 会「做不完」或「糊弄」）
- 过细：任务数远超 3–5 个（编排成本、通信开销失控）
- 经验法则：复杂任务拆 3–5 个子任务（《Hello-Agents》第 14 章同款判据）

### 3. 能力单元设计（四类资源）

- **角色**：单 Agent 还是多 Agent？判据是「复杂度爆炸点」而非功能数量——单 Agent 工具太多、中间结果靠参数传递混乱时再拆多 Agent。
- **工具**：列出每个任务需要的外部能力（搜索/数据库/计算/第三方 API），先判「能否用现有 MCP 服务」，不要急着造。
- **记忆**：哪些状态需要跨会话保留？对应工作/情景/语义/感知哪类记忆（详见 `agent-memory-rag-design`）。
- **范式**：该任务偏探索型（ReAct）／逻辑确定型（Plan-and-Solve）／高准确性（Reflection）？（详见 `agent-paradigm-selection`）

### 4. 边界与验收（DoD 清单）

- **范围约束**：明确「不做」清单（越界即拒），比「做」清单更能防蔓延。
- **定量指标**：准确率、召回、成功率、平均步数、成本上限——每个给可测阈值。
- **失败模式预判**：列出最可能的 3 种失效及兜底策略（如检索失败→回退 LLM 自身知识）。
- **成本预算**：单次交互 token 上限、日调用上限（对应 `agent-delivery-ops` 的护栏）。

## A1 — 案例

**案例 1：客服工单自动化（适用性判定的反面教材）**
场景：企业想把「工单分类」用 Agent 做。做法：先判适用性——工单分类是规则可穷举的确定性流程，用 Agent 是「杀鸡用牛刀」且引入不确定性。可迁移教训：**「能不能做」不等于「该不该做」**，先过四象限再谈方案；只有「疑难工单的意图理解与转人工决策」这类模糊环节才真正适合 Agent。

**案例 2：旅行规划助手（任务拆解示范）**
场景：把「帮我做旅行规划」拆成 Agent 方案。做法：业务目标「按需产出行程」→ 拆 4 个任务（搜景点、查天气、定酒店、排日程）→ 每个任务一个 Agent + 各自工具（搜索/天气/酒店 API）→ Pydantic 自底向上定义数据契约（Location→Attraction→DayPlan→TripPlan）→ DoD 定义「行程可执行、含天气适配、预算内」。可迁移教训：**先定数据契约再拆角色**，跨 Agent 的接口是需求阶段就要锁死的，不是开发时补的。

## A2 — 触发场景

- 用户说「我想用 Agent 做 X，帮我评估该不该做、怎么做」
- 用户给了一段业务需求，要求产出「Agent 产品技术方案」
- 需求已开始做但出现范围蔓延 / 验收扯皮，需重新界定边界
- 需要把「一个模糊的产品想法」落到「任务/角色/工具/验收」四清单

## E — 执行步骤

1. **判断适用性**：按四象限逐维打分，产出「该不该用 Agent + 理由 + 建议技术栈」的判断。
2. **拆解任务**：产出任务清单表（任务/输入/输出/成功标准/依赖），控制在 3–5 个主任务。
3. **设计能力单元**：为每个任务标注所需的角色、工具、记忆、范式，标注「用现有 MCP 还是自建」。
4. **定义验收**：产出 DoD 清单（范围约束 + 定量指标 + 失败模式 + 成本预算）。
5. **输出需求规格**：汇总为一份「Agent 需求规格」（Goal → Tasks → 能力单元 → DoD），作为设计与开发的输入。

## B — 边界与失效条件

**不该用本 skill 的情况**：需求已经是明确的技术选型问题（直接走 `agent-paradigm-selection` 等设计 skill）；或用户只是要「修一个已有 Agent 的 bug」（属开发/调试，非需求分析）。

**已知失效模式**：
1. **过度自动化**：把确定性流程硬上 Agent，引入不确定性还更贵——四象限没拦住。
2. **范围蔓延**：只列「做」不列「不做」，越做越多，永远交付不了。
3. **拆解过粗/过细**：过粗则单个 Agent 决策超载，过细则编排成本失控，两头都导致不可交付。
4. **验收标准空转**：用「好用」「准确」这种不可测的词当验收，交付时无据可依。
5. **边界与数据契约后置**：跨 Agent 接口留到开发时定，导致返工。

**成本代价**：需求分析本身零 token 成本，但**错误的适用性判定是最贵的一步**——把整个产品建在错误的技术栈上，代价是全部推倒重来。

## 配套技能

本技能是 **AI Agent 全生命周期套件**（`zen-agent-suite`）的第 1/10 环。
从需求分析到交付运维，覆盖构建一个 AI Agent 产品的完整链路。

> **只装本技能不足以覆盖完整需求。** 若你正在做的是「创建 AI Agent/搭建智能体」这类完整任务，建议一并安装同套件的其他 9 个技能 —— 它们分别负责需求、设计、验证、运维等环节，缺环会导致流程断在中途。

**同套件技能**（按推荐使用顺序）：

| 阶段 | 技能 | 作用 |
|---|---|---|
| ① 需求 | `agent-requirement-analysis` ← **本技能** | 判断该不该用 Agent、拆解任务与定义验收标准 |
| ② 设计 | `agent-paradigm-selection` | 选 ReAct / Plan-and-Solve / Reflection 范式 |
| ② 设计 | `agent-framework-architecture` | 框架选型与分层架构设计 |
| ② 设计 | `agent-memory-rag-design` | 记忆系统与 RAG 检索链路设计 |
| ② 设计 | `agent-context-engineering` | 上下文工程与 GSSC 流水线 |
| ② 设计 | `agent-protocol-selection` | MCP / A2A / ANP 协议选型与集成 |
| ② 设计 | `multi-agent-orchestration` | 多智能体协作编排与成本控制 |
| ③ 验证 | `agent-evaluation-loop` | 评估系统搭建与改进闭环 |
| ④ 运维 | `agent-delivery-ops` | 交付上线、成本控制与安全护栏 |
| ⑤ 进阶 | `agentic-rl-pipeline` | Agentic-RL 训练流水线（可选进阶） |
